# 衡策 · 财务智能审核系统

衡策（Finwise）是一套面向小微企业和中小企业的发票识别与报销智能审核工作台。

系统的核心不是单纯展示 OCR 结果，而是围绕一笔报销能否通过，建立完整的财务决策链路：

```text
票据接入
→ OCR 结构化识别
→ 发票验真
→ 重复发票与黑名单检测
→ 业务规则审核
→ 审核优先级评分
→ 自动决策路由
→ 人工复核
→ 支付与预算结转
→ 审核日志和规则优化反馈
```

当前版本是可运行、可交互的前端演示系统。核心领域逻辑已经从页面中分离，但 OCR、税务验真、数据库、对象存储和支付渠道仍使用 Mock 或本地模拟。

### PaddleOCR 本地服务

项目新增 `ocr-service`，用于接入真实的中文票据 OCR。安装 Python 3.10+ 后执行：

```bash
cd ocr-service
pip install -r requirements.txt
uvicorn main:app --host 127.0.0.1 --port 8001
```

接口为 `POST http://127.0.0.1:8001/api/ocr/invoice`，使用 `multipart/form-data` 字段 `file` 上传 JPG、PNG、WebP 或 PDF。服务返回发票号码、日期、购销方、税额、价税合计和原始 OCR 文本。生产环境应将该服务放在内网，通过鉴权网关调用，并增加文件病毒扫描、任务队列、超时重试和结果人工确认。

## 登录与角色入口

系统采用企业账号密码登录，并按用户身份进入不同工作台：

| 身份 | 演示账号 | 密码 | 登录后能力 |
| --- | --- | --- | --- |
| 普通员工 | `employee@xinghai.com` | `Employee@2026` | 提交多张票据、保存草稿、修改、撤回、补充材料、查看本人进度与面向员工的处理建议 |
| 财务人员 | `finance@xinghai.com` | `Finance@2026` | 进入完整财务审核工作台，认领、转派、审核、支付处理、预算和规则管理 |

员工入口始终按 `employeeId` 隔离数据，不能通过 URL 进入财务审核界面，也不会展示风险评分、规则编号、证据链或内部审核意见。被驳回的申请会保留原记录；员工可基于原申请新建一笔修改后的申请，便于审计追溯。

员工提交后，票据元数据与申请会写入浏览器本地持久化，并进入财务人工审核队列。草稿不冻结预算；财务通过时冻结预算，支付成功后转为实际支出。演示账号和浏览器本地会话仅用于展示，生产环境必须由服务端实施密码哈希、MFA、短期会话令牌、RBAC 与租户级数据隔离。

## 核心业务模型

### 工作流状态

报销业务状态与机器决策、人工决策、支付状态已经拆分，避免使用一个字段表达所有含义。

```text
DRAFT
→ SUBMITTED
→ OCR_PROCESSING
→ WAITING_FIELD_CONFIRMATION / VERIFYING
→ AUDITING
→ WAITING_MANUAL_REVIEW / WAITING_SUPPLEMENT / SUSPENDED
→ APPROVED / REJECTED
→ PAYMENT_PENDING
→ PAID / PAYMENT_FAILED
```

`REJECTED`、`PAID` 和 `CANCELLED` 是默认终态。状态变化必须通过状态机校验，不能从终态直接跳回审核中。

### 决策类型

系统支持以下决策：

- 自动通过
- 驳回
- 人工复核
- 挂起
- 要求补充材料
- 升级审批

机器决策保存在 `machineDecision`，人工最终结果保存在 `finalDecision`，不会互相覆盖。

### 支付状态

支付状态独立于报销审批状态：

```text
NOT_STARTED
→ QUEUED
→ PROCESSING
→ PAID / FAILED
```

支付失败后可以重新进入支付队列。失败期间预算仍保持冻结，避免释放额度后产生超支。

## 规则引擎

规则不是在前端执行任意字符串表达式，而是通过受限 AST 描述：

```ts
interface RuleCondition {
  field: RuleField;
  operator: RuleOperator;
  value?: string | number | boolean;
}

interface RuleGroup {
  combinator: 'AND' | 'OR';
  conditions: Array<RuleCondition | RuleGroup>;
}
```

支持的主要操作符：

- `EQ` / `NEQ`
- `GT` / `GTE`
- `LT` / `LTE`
- `CONTAINS` / `NOT_CONTAINS`
- `EXISTS`

每条规则包含版本、生命周期、灰度比例、生效时间、优先级和是否阻断等字段。审核记录会保存实际使用的规则版本。

### 规则冲突策略

同时命中多条规则时，按以下顺序决定最终出口：

```text
阻断规则
→ 动作优先级
→ 风险等级
→ 规则优先级
```

动作优先级为：

```text
驳回
> 挂起
> 升级审批
> 要求补充材料
> 人工复核
> 自动通过
```

## 审核优先级评分

系统使用“审核优先级分”，不是简单将数字命名为风险分。

- 分数高：更适合自动处理
- 分数低：更需要人工关注

当前示例会考虑：

- 小额报销
- 高额报销
- 员工信用
- 紧急业务
- 重复发票
- 购买方错误
- 超预算

规则负责确定性底线，评分负责排序和路由辅助，评分不能覆盖阻断规则。

## 发票识别与验真

### 文件校验

上传前会校验：

- 文件不能为空
- 文件大小不超过 10MB
- 仅允许 JPG、PNG、WebP 和 PDF

浏览器 `accept` 只是交互提示，真实系统还需要在服务端校验 MIME 魔数、页数并执行病毒扫描。

### OCR

`OcrService` 返回字段级置信度和是否需要人工确认，而不是直接返回未经验证的完整发票对象。

当前 OCR 使用 Mock 数据，但保留了：

- 请求超时
- 文件校验
- 失败状态
- 缺失字段检测
- OCR 结果到发票草稿的显式转换

### 验真

验真结果区分：

- 验真通过
- 信息不一致
- 发票作废
- 发票红冲
- 发票不存在
- 技术异常

业务失败可以触发驳回；网络超时、限流或服务不可用属于技术失败，应降级为人工处理，不能伪装成假票。

## 重复发票检测

系统根据以下字段生成规范化指纹：

```text
发票代码
+ 发票号码
+ 开票日期
+ 价税合计
+ 销方税号
```

指纹生成前会处理：

- Unicode 全角和半角差异
- 空格
- 横线
- 大小写
- 金额小数位

查重时会排除当前发票自身，并限制在当前租户内查询。

## 预算事务

预算可用金额公式：

```text
可用预算 = 总预算 - 实际支出 - 冻结金额
```

业务过程：

```text
提交或通过
→ 创建冻结记录

驳回或撤回
→ 释放冻结金额

支付成功
→ 冻结金额减少
→ 实际支出增加

支付失败
→ 保留冻结金额
→ 等待重试
```

预算操作使用 `idempotencyKey` 防止重复冻结，并通过版本字段模拟乐观并发控制。

## 人工审核任务

人工复核支持：

- 认领任务
- 释放任务
- 转派任务
- 两小时 SLA
- 超时识别
- 审核本人报销限制
- 高金额审批权限检查

人工处理必须填写审核意见。处理后会记录机器结论、人工结论、前后状态、规则版本、审核人和 traceId。

## 权限与多租户

当前领域模型包含：

- `tenantId`
- `SessionUser`
- `Role`
- `Permission`
- `AuthorizationService`

演示环境中的当前用户是财务负责人。权限校验已经在领域服务中执行，但真实生产环境必须在服务端再次校验，不能依赖前端隐藏按钮。

所有核心数据和查询都应强制携带租户条件，避免跨公司读取发票、员工、预算和审核记录。

## 审计与幂等

每次人工决策和重新审核都会生成审核记录，包含：

- 报销编号
- 操作时间
- 机器结论
- 人工结果
- 审核人
- 前后状态
- 规则集版本
- traceId
- 审核意见

审核命令使用“报销单号 + 决策 + 当前版本”生成幂等标识，重复提交时不会重复执行。

浏览器演示日志可以被本地用户修改。生产系统必须由服务端生成只追加、不可覆盖的审计日志。

## 数据持久化

当前状态保存在浏览器：

```text
localStorage key: finwise-demo-v4
```

持久化内容包括：

- 报销单
- 预算
- 规则
- 审核记录
- 预算冻结记录
- 幂等命令记录

读取时会验证 Schema 版本和租户。升级数据结构时使用新的 Schema 版本，避免旧数据破坏页面。

清除浏览器站点数据后，系统会恢复初始 Mock 数据。

## 导出安全

发票、预算、风险事件和审核日志支持 CSV 导出。

导出工具会对以 `=`、`+`、`-`、`@` 开头的字段增加前缀，降低 CSV 公式注入风险。

真实系统还需要增加：

- 导出权限
- 敏感字段脱敏
- 导出审批
- 文件水印
- 导出审计日志

## 生产化建议

推荐的生产架构：

```text
React 管理后台
→ API Gateway / BFF
→ 报销服务
→ 发票服务
→ 规则与决策服务
→ 预算服务
→ 审批任务服务
→ 支付服务
→ 审计服务

PostgreSQL + Redis + 对象存储 + 消息队列
```

生产化时应优先完成：

1. 将 `PersistenceService` 替换为服务端 Repository/API Adapter。
2. 在数据库事务中完成预算冻结、释放和扣减。
3. 为发票指纹增加租户内唯一索引和历史状态规则。
4. 将 RBAC、租户隔离和职责分离移到服务端强制执行。
5. 将审计日志改为服务端只追加存储。
6. 对 OCR、验真和支付接口增加重试、熔断、死信队列和告警。
7. 使用对象存储保存发票原件，并进行病毒扫描和访问授权。
8. 将规则版本、发布、灰度、回滚和样本回放接入持久化规则库。

系统的基本原则保持不变：

> 规则决定底线，数据决定判断，AI 负责识别、解释和辅助决策，人工负责最终兜底。
